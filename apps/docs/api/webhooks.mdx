title: "Webhook triggers"
description: "Start a coworker run from any service that can send an HTTP request."
---

A trigger gives a coworker a public URL. Call that URL and the coworker starts working. There is no SDK, no key exchange and no handshake: anything that can send an HTTP request can fire a coworker.

```
https://app.rerun.build/api/t/{agentId}/{slug}/{token}
```

Create a trigger in the app under the coworker **Triggers** tab, or with [`upsert_trigger`](/api/tools/triggers#upsert_trigger). Both give you the full URL.

## The URL is the credential

There is no signature, no secret header and no allowlist. Whoever holds the URL can fire the coworker, as many times as they want.

<Warning>
  Treat every trigger URL like a password. Do not paste it into a shared document, a ticket or a public repository. If one leaks, rotate it with [`rotate_trigger_token`](/api/tools/triggers#rotate_trigger_token) or from the **Triggers** tab, and update every service configured with it.
</Warning>

Because the URL is the whole authentication, Rerun cannot validate a third-party signature header today. Caller headers are never forwarded to the coworker: they carry credentials and are trivially spoofed.

## Methods

A trigger declares which HTTP methods it accepts. The default is `POST` alone.

`GET`, `POST`, `PUT`, `PATCH` and `DELETE` all reach the same handler. `HEAD` and `OPTIONS` never start a run.

<Note>
  Accepting `GET` means a link preview, a prefetch or a crawler could fire your coworker by touching the URL. Rerun filters out [passive visits](#passive-visits), but keep `POST` unless the calling service cannot send it.
</Note>

## What the coworker receives

The coworker gets the trigger `body`, which is the instruction you wrote, followed by the caller payload in a `<trigger_payload>` block:

```
Read the Stripe payload and add a row to the payments table.

<trigger_payload trigger="stripe-payment" method="POST" received="2026-08-15T09:12:04.000Z" content-type="application/json" bytes="412">
{
  "type": "payment_intent.succeeded",
  "data": { … }
}
</trigger_payload>
```

The opening tag also carries `query="…"` when the URL had a query string, and `truncated="true"` when the payload was cut. A call with an empty body hands over `(no payload)` inside the block.

JSON is pretty-printed. The payload is truncated at 64 KB, with a closing line that gives its full size in bytes. Any closing tag inside the payload is escaped, so a caller cannot inject instructions by ending the block early.

Each call opens a new session named `trigger: <slug>`. Two calls are always two runs: nothing is collapsed or debounced.

## Response codes

The call returns as soon as the run has started. It does not wait for the coworker to finish.

| Code | Body | When |
| --- | --- | --- |
| `202` | `{ "runId": "…", "sessionId": "…", "trigger": "…" }` | The run started |
| `204` | empty | Passive visit, or `OPTIONS` |
| `200` | empty | `HEAD` |
| `405` | `{ "error": "Method not allowed" }` plus an `Allow` header | The trigger does not accept that method |
| `413` | `{ "error": "Payload too large" }` | Body over 1 MB |
| `404` | `{ "error": "Not found" }` | Everything else |

That last row is deliberate. A malformed slug, a missing token, an unknown or switched-off coworker, a wrong token, a disabled trigger, a machine that did not acknowledge the call within 15 seconds and an engine that turned the call away all answer `404`, so nobody can probe which triggers exist on your account.

## Passive visits

Link unfurlers, prefetchers, clipboard managers and browsers touch URLs without anyone meaning to call them. Rerun answers those with `204` and never starts a run, whatever the method, before it even reads the body. A request counts as a passive visit when:

- its `User-Agent` is a bot or a link previewer: Slack, Discord, Twitter, Facebook, WhatsApp, Telegram, LinkedIn, Reddit, Skype, Bing, Embedly, iframely, Quick Look, Raycast, Paste, Maccy, or anything that calls itself a bot, a crawler, a spider, a preview or an unfurler
- it carries a prefetch, prerender or preview intent in `Sec-Purpose`, `Purpose`, `X-Purpose` or `X-Moz`
- it is a browser navigation: a `Sec-Fetch-Dest` header with any value other than `empty`, which is what opening the URL in a tab sends

A server-to-server webhook sends none of these, so it goes through. Pasting a trigger URL into a chat or opening it in a browser is still a leak, but it will not fire your coworker by itself. A `fetch()` from a web page sends `Sec-Fetch-Dest: empty` and does fire it.

## Limits

| Limit | Value |
| --- | --- |
| Request body | 1 MB, `413` above |
| Payload handed to the coworker | 64 KB, truncated |
| Time the front door waits for the machine to acknowledge | 15 seconds |
| Rate limit | None |

## Testing

Fire it yourself with `curl`:

```bash
curl -i -X POST "https://app.rerun.build/api/t/AGENT_ID/SLUG/TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"event":"test"}'
```

Or use [`test_trigger`](/api/tools/triggers#test_trigger), which pre-checks the method and the enabled state so you get a readable error instead of a bare `404`. Either way it is a real fire: it counts towards the trigger fire count.

Read the outcome with [`get_run`](/api/tools/runs#get_run), using the `runId` from the `202`.
